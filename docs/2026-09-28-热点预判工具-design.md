## 第 1 节 · 整体架构与数据流 【已确认】

```
[采集层 collectors]  →  [存储 SQLite]  →  [评分引擎 scoring]  →  [LLM 分析 llm_judge]  →  [输出 render]
   知乎/B站/微博/海外源      signals 表         复合分+双档信号         赛道匹配+爆款基因      日报.md + 看板.html
   统一接口 Collector        snapshots 表       快讯级(1-6h)            评级 A/B/C + 理由     Windows 任务计划定时
                            topics 表          趋势级(3-7d)
```

**数据流（一轮运行）**：

1. **collect**：各平台采集器拉当前榜单/话题/关键词，标准化成 `signal` 记录（来源、标题、链接、互动数、发布时间、账号权重）
2. **store**：写入 SQLite，按 `(topic_key, source, ts)` 去重；同一话题跨平台同 `topic_key` 聚合
3. **score**：对每个 topic 计算复合分 = 增速(环比互动) + 互动率 + 账号权重 + 跨平台共振数；同时分桶到**快讯级**（近 6h 突增）和**趋势级**（3-7 天连续上行）
4. **judge**：双档 Top-N 进 LLM，输出赛道匹配（5赛道）、爆款基因、评级 A/B/C + 一句理由
5. **render**：生成 `日报/YYYY-MM-DD.md`（快讯栏 + 趋势栏）+ 刷新 `看板/index.html`（静态，浏览器直开）

**关键决策**：

- **接口留缝（为方案C）**：采集器统一 `Collector.fetch() -> list[Signal]`，将来换 sansan0/TrendRadar 只写一个新 Collector，评分/LLM/输出层不动
- **SQLite 单文件**：零部署，`热点.db`，历史数据留着算环比增速（增速是核心信号，没历史算不了）
- **定时**：Windows 任务计划，快讯级每 2h、趋势级+日报每天 1 次
- **LLM 可降级**：无 key 或超时时，日报标注"仅机械评分"，评级留空——工具不因 LLM 挂掉而停摆

**目录草案**：
```
热点预判/
  collectors/  scoring/  llm_judge/  render/
  热点.db
  日报/  看板/
  config.yaml   ← 赛道关键词、权重、平台开关
```

## 第 2 节 · 采集层 【已确认】

### 2.1 数据源清单（首期）

| 源 | 抓什么 | 接口性质 | 用途档位 | 风险 |
|---|---|---|---|---|
| 知乎热榜 | 热榜 20 条 + 话题热度值 | 网页 API，无需登录 | 快讯+趋势 | 中（接口偶变） |
| B站热搜/排行榜 | 热搜词 + 排行榜视频互动数 | 官方 api.bilibili.com | 快讯+趋势 | 低（部分接口需 wbi 签名） |
| 微博热搜 | 热搜词 + 热度 + 榜位变化 | m.weibo.cn 容器接口 | 快讯 | 中（需 Cookie，反爬最严） |
| HackerNews | 前 30 + 分数增速 | 官方 API，无 key | 趋势（科技） | 低 |
| Reddit r/popular | 帖子分数 + 评论增速 | 公开 .json 端点 | 趋势（海外辅信号） | 低 |
| GitHub Trending | 当日新星仓库 | 抓 HTML | 趋势（AI工具） | 中 |

**诚实标注**：上表接口路径是通行做法，但全部**必须经第 0 步"连通性探针"实测**再定稿——接口会变、会加签名、会封 IP。探针脚本 `probe.py` 逐源测试，输出 PASS/FAIL/需Cookie，探针不过的源降级为"暂不启用"，不阻塞整链路。

**微博特殊处理**：反爬最严，策略是——能用 Cookie 就用（用户手动登录一次导出 Cookie，存本地 `config.yaml`，过期重导）；拿不到就自动跳过，热搜改由知乎热榜+其他源的"微博话题"间接信号补位。**零成本方案不买代理**，靠频率限制（每源 ≥5 分钟间隔 + 随机 UA + 单线程）保命。

### 2.2 统一 Signal 接口

```python
@dataclass
class Signal:
    topic_key: str      # 聚合键：归一化标题的 hash（去空格/标点/大小写）
    source: str         # zhihu/bilibili/weibo/hn/reddit/github
    title: str
    url: str
    heat: float         # 平台原始热度（各源自校准到 0-100）
    rank: int           # 榜位（1起）
    rank_delta: int     # 与上轮相比的榜位变化（升为正）
    engagement: float   # 互动量（赞/评/转 统一口径）
    author_weight: float# 账号权重 0-1（认证媒体/大V/普通）
    published_at: datetime
    fetched_at: datetime
    raw: dict           # 原始响应，存档供排错

class Collector(Protocol):
    name: str
    def fetch(self) -> list[Signal]: ...
```

**跨源聚合**：`topic_key` 归一化后，同一事件在知乎+微博+B站都出现 → 一条 topic 多条 signal → **跨平台共振数**（≥3 源命中是强趋势信号，直接进评分加成）。

**热度自校准**：各源原始量纲差 10 个数量级（微博热度 vs HN score），每个 Collector 内部做源内百分位归一（rank/榜单长 → 0-100），**不做跨源绝对值比较**——只比"各源内的相对位置"和"同一源的时间序列变化"。

### 2.3 存储

```sql
signals(id, topic_key, source, title, url, heat, rank, rank_delta,
        engagement, author_weight, published_at, fetched_at, raw)
-- UNIQUE(topic_key, source, fetched_at) 防重
-- 索引: topic_key, fetched_at
```

每轮全量写入，不 UPDATE——增速计算靠时间序列查询，不靠差值字段。

## 第 3 节 · 评分引擎 【已确认】

### 3.1 复合分公式

每个 **topic**（跨源聚合后）每轮算一次：

```
score = w1·增速分 + w2·互动率分 + w3·账号权重分 + w4·共振分 + w5·榜位分
```

| 分量 | 计算 | 权重(初值) |
|---|---|---|
| **增速分** G | (本轮 engagement − 上轮 engagement) / 上轮 engagement，近 4 轮滑动窗口取最大，归一 0-100。新话题无历史 → 用 rank_delta 折算（升 10 位 = 60 分） | 0.35 |
| **互动率分** E | engagement / heat（或 /曝光量），源内百分位归一 0-100 | 0.25 |
| **账号权重分** A | topic 内最高 author_weight ×100（官媒/认证 > 大V > 普通） | 0.15 |
| **共振分** R | 命中源数：1源=0 / 2源=40 / 3源=70 / ≥4源=100 | 0.15 |
| **榜位分** K | (榜单长 − rank) / 榜单长 ×100；含 rank_delta 加成（升位=+15，封顶） | 0.10 |

**权重放 `config.yaml`**，可调；初值给的是"抢时效"偏置（增速最重）。

### 3.2 双档信号定义

两档**独立分桶**，同一 topic 可同时进两栏：

**快讯级（1-6h 提前量）——抓"正在起爆"**
```
命中条件（满足任一）：
  N1. 增速分 G ≥ 80 且 age ≤ 6h        ← 短时暴增
  N2. rank_delta ≥ 10（榜位 6 小时内升 10+ 位）
  N3. 新话题首次出现即 heat ≥ 70        ← 开屏即高热（突发事件）
取：score 降序 Top 10，age > 6h 自动出桶
```

**趋势级（3-7 天提前量）——抓"正在成型"**
```
命中条件（全部满足）：
  T1. 连续 ≥ 3 个采样日上榜（不一定是榜一，只要在榜）
  T2. 7 日 trend_slope > 0（线性回归斜率，engagement 或 rank 均可）
  T3. score ≥ 50
  T4. 跨源共振 ≥ 2（单一源的自嗨不算趋势）
取：score 降序 Top 15，满 7 天未爆 → 转入"长尾观察"或出桶
```

**关键差异**：快讯看**一阶导**（短窗爆发），趋势看**多日形状**（持续上行 + 多源共振）。这是两套独立的窗口查询，不是同一条阈值线。

### 3.3 阈值与冷启动

- 所有阈值（80/70/50、Top N、窗口长度）全在 `config.yaml`，第一版给上表初值
- **冷启动**：前 3 轮采样（约 6h）只有快讯级可用（没历史算不了趋势斜率）；趋势级第 4 轮起自动启用，日报里标注"趋势栏数据积累中"
- **出桶不删除**：topic 留在库里，供 LLM 做"回看复盘"（哪些 A 级真爆了、误判在哪）→ 用于将来调权重

## 第 4 节 · LLM 分析层 【4.1-4.4 已确认 · 4.5 待决策】

### 4.1 位置与输入

LLM **只处理双档 Top-N 进桶的 topic**（快讯 Top10 + 趋势 Top15，去重后每轮 ≤20 条），不是全库扫——控制成本（单轮约 10-15K tokens，每天快讯 12 轮 + 趋势 4 轮 ≈ 200K tokens/天内）。

**输入给 LLM 的 topic 包**：
```json
{
  "title": "...", "sources": ["zhihu:#3", "weibo:#1", "bilibili:#5"],
  "score": 87, "tier": "快讯", "age_hours": 2,
  "heat_trend": [40, 55, 78, 91],
  "top_signals": [{"title": "知乎原题", "excerpt": "首条回答前200字"}],
  "matched_keyword": "AI工具"
}
```
给**标题 + 1-2 条原声摘录**，不给全文——判断"这是什么、会不会爆"不需要通读。

### 4.2 单次调用输出（结构化 JSON）

```json
{
  "rating": "A",
  "track": "AI/科技工具",
  "hook_reason": "一句话：为什么它可能爆/正在爆",
  "genre_score": 0,
  "fit_score": 0,
  "angle": "若做内容，切入角度一句话（选题用）",
  "act_now": "快讯级专属：建议几小时内发，晚了会怎样",
  "risk": "翻车风险/过审风险（社会新闻类必填）"
}
```
**严格 JSON 输出**，解析失败 → 该 topic 降级为"仅机械评分"并记日志，不重试超过 2 次。
（genre_score/fit_score 为 0-10 分）

### 4.3 评级规则（prompt 写死判据）

```
A 级（立即行动）：genre ≥ 8 且 fit ≥ 7 且 时效窗口内   → 日报置顶 + 看板红标
B 级（值得跟）  ：genre ≥ 6 或 fit ≥ 8，二者至少一强    → 日报正文
C 级（观察）    ：其余进桶的                          → 日报折叠栏
```
- **genre（爆款基因）四维**：情绪浓度（愤怒/爽/恐惧/惊奇）、冲突性（对立立场/利益剥夺）、身份相关（"跟我有关"）、意外度（信息差）
- **fit（赛道匹配）**：5 赛道各配关键词表，`config.yaml` 维护；LLM 负责**语义判断**（关键词表可能没命中，但语义上属于对应赛道）

### 4.4 模型选择与降级

| 项 | 决策 |
|---|---|
| 模型 | opencode provider 的 mimo-v2.6-flash-free（见 4.5） |
| 超时 | 单 topic 15s，整轮 90s 上限 |
| 降级 | 无 key / 全超时 / 配额尽 → 日报栏头标"⚠️ 本日未过 LLM，仅机械排序"，C 级以上留空，**快讯/趋势两栏照常输出** |
| 缓存 | 同 `topic_key` + 同 tier，24h 内不重复调用（topic 持续在榜时省钱） |

### 4.5 【已确认·2026-09-28 变更】模型选型：deepseek provider

> **实施变更（用户拍板）**：原定 opencode zen 免费层在实测中返回 403 FreeTierError: OpenCode's free tier can only be used from within OpenCode，即 **opencode provider 拒绝外部 Python 进程调用**，定时任务方案下不可用。备选实测：bigmodel/siliconflow 余额不足（429/402）、tokenrouter 礼金 （403）、openrouter 余额仅剩 326 token（402）、volcengine 模型未开通（404）。**deepseek-chat 实测 200 且 JSON 输出正确（单次约 70 token）**，故主模型改为 deepseek-chat。

**原决策（已作废，留档）**：直接用当前会话所用的 LLM——opencode 配置里的 `opencode` provider。

| 项 | 值 |
|---|---|
| 配置文件 | `C:\Users\Admin\.config\opencode\opencode.json` → `provider.opencode` |
| baseURL | `https://opencode.ai/zen/v1`（OpenAI 兼容 /chat/completions） |
| key | 配置内已存（**运行时读配置文件，禁止硬编码进代码**，符合零成本+不泄密规则） |
| 主模型 | `mimo-v2.6-flash-free`（当前会话同款） |
| 备选模型链 | `deepseek-v4-flash-free` → `hy3-free` → `glm-4.5-flash` → `moonshotai/kimi-k3-free`（opencode / tokenrouter / bigmodel / tokenrouter1 四个 provider 均已配 key） |
| 兼容性 | 标准 OpenAI SDK 或裸 requests 均可，无需新依赖 |

**实现要点**：
1. 启动时读 opencode.json 拿 baseURL + apiKey + model，**不落任何 key 到本项目文件/日志**
2. 首轮跑一次 `probe_llm.py`：验证主模型可用 + JSON 模式输出正常；不可用则按备选链降级，并把可用模型写进 `config.yaml`
3. 连续 3 次失败自动切下一个备选模型；全挂 → 触发 4.4 降级（仅机械评分）
4. 日报中标注实际使用的模型名，便于回看哪次评级是哪个模型出的

## 第 5 节 · 日报与看板 【已确认】

### 5.1 日报（Markdown，主交付物）

`热点预判\日报\2026-09-28.md`，每天 08:00 生成当日首版，之后每轮快讯覆盖更新（同文件永远是最新态）。

```markdown
# 热点日报 · 2026-09-28 （模型：mimo-v2.6-flash-free · 采样 12 轮 · 更新 14:00）

## 快讯（1-6h 窗口）
### [A] 某AI公司发布开源模型，3小时刷屏        <- 红标
- 爆点：开发者身份相关 + 意外度（小团队干翻大厂）
- 基因 9/10 · 匹配 8/10 · sources: 知乎#2 微博#1 B站#5
- 切入角度：实测它能不能替代你正在用的那款
- 动作：4 小时内发，晚了热度被头部账号吃掉
- 风险：无
- 趋势线：40 -> 55 -> 78 -> 91
### [B] ...（B级正文）
### [C] ...（折叠）

## 趋势（3-7 天成型中）
### [B] 某副业话题连续5天上榜，跨3源共振
- 5日斜率 +38% · sources: 知乎/B站/Reddit
- 切入角度 / 风险（无 act_now）

## 观察（C级，折叠）

## 复盘（隔日自动生成）
- 昨日 A 级 3 条：真爆 2 / 误判 1（附原因）
```

要点：
- A 级置顶 + 每条必带切入角度（这是选题产出，不是数据报表）
- 复盘栏：次日对比昨日 A 级话题的实际热度，写入复盘表，供调权重（对应 3.3 出桶不删除）
- 表头标注模型名 + 采样轮数 + 最后更新时间，降级状态一眼可见

### 5.2 推送渠道 = Server酱（安卓手机 + 微信）

| 项 | 值 |
|---|---|
| 服务 | Server酱·Turbo sct.ftqq.com，微信扫码登录拿 SendKey |
| 成本 | 免费档 5 条/天 |
| 用量预算 | 日报 1 条 + A级快讯即时追加 2 条 = 全天 3 条（留 2 条余量） |
| 推送策略 | 1) 日报生成推全文摘要（前3条A级+看板路径）2) 快讯档出现 A 级立刻单推 1 条（B/C 不打扰）3) 降级/异常推 1 条告警 |
| SendKey | 用户扫码后提供，存 config.yaml（不硬编码、不进日志），缺失时退回 Windows Toast 本地通知 |

实现：notifier.py 统一 notify(title, content, level)；Server酱失败（网络/key失效）-> 回退 Toast -> 记日志，日报文件照常落盘（推送失败不影响产出）。

### 5.3 看板（静态 HTML，零服务器）

`热点预判\看板\index.html`，本地双击打开，每轮 render 覆盖刷新：

- 顶部：A/B/C 计数、双档命中数、数据新鲜度（最后采样时间）、模型名/降级状态
- 快讯流：时间倒序卡片，红(A)/黄(B)/灰(C) 色标，展开显示趋势折线（内联 SVG，无外部 JS 库）
- 趋势流：按在榜天数 + 斜率排序，显示跨源标记
- 回看页：近 7 天所有 A 级 + 复盘结果（真爆/误判）
- 技术：纯静态单文件 HTML + 内嵌 JSON 数据，无 CDN、无框架、无网络请求，离线可看

### 6.2 错误处理（每层独立失败，不连锁）

| 层 | 失败 | 处理 |
|---|---|---|
| 采集 | 某源超时/反爬/结构变更 | 该源本轮跳过+记日志，连续失败3次自动禁用到次日；其余源照常；全部挂则用上轮缓存跑后续链路并标注数据陈旧 |
| 存储 | DB锁/写失败 | 重试1次，失败则本轮终止，不产出半截日报 |
| 评分 | 无历史（冷启动） | 按3.3走快讯-only |
| LLM | 超时/JSON解析失败 | 单topic重试2次后降级为仅机械评分；全挂则日报标降级 |
| 推送 | Server酱网络/限额 | 回退Toast；都不影响日报文件落盘 |
| 任务计划 | 错过调度 | Windows任务计划错过后立即补跑，main.py幂等（同轮重复跑不产生重复数据） |

统一日志 logs\run-*.log：每轮一行摘要（各源信号数/进桶数/LLM调用数/耗时/错误）。

### 6.3 测试（不搞重框架，三条命令）

1. 探针：python probe.py 输出6源 PASS/FAIL 表；python probe_llm.py 输出模型+JSON模式 PASS/FAIL（每次改接口先跑）
2. 单测：tests\ 下只测三块易错逻辑——topic_key 归一化（同一事件不同写法聚到一起）、复合分数学（断言分数）、双档分桶边界（6h出桶/连续3日判定）
3. 端到端干跑：python main.py --dry-run 用录制固定原始响应（tests\fixtures\）跑全链，比对日报黄金样本，不发真请求不花钱；验收时连跑3天真实数据

## 第 7 节 · 实施顺序与验收 【已确认】

### 7.1 分6步，每步有独立可验证的产出

| 步 | 内容 | 产出 | 验收（机器可查） |
|---|---|---|---|
| S0 探针 | probe.py + probe_llm.py | 探针报告 | 6源中至少4 PASS（知乎/B站/HN必须过，微博允许缺Cookie降级）；主模型JSON输出 PASS |
| S1 采集+存储 | 6个Collector + db.py + Signal接口 | 连跑3轮的真实signals | SQLite有数据、去重生效、topic_key归一化单测过 |
| S2 评分 | score.py + buckets.py | 双档分桶结果 | 单测过（分数学/6h出桶/3日趋势）；冷启动只出快讯不报错 |
| S3 LLM | judge.py + prompt.py + 降级链 | 结构化评级JSON | 真调用≥20 topic解析成功率>90%；断网演练自动降级不崩 |
| S4 输出 | report.py + board.py + notifier.py | 日报+看板+微信推送 | 日报含A/B/C+切入角度；看板离线双击可开；收到微信 |
| S5 定时+验收 | Windows任务计划 + 3天试运行 | 连续3天日报 | 3天无中断、每份日报A级≤10、复盘栏次日出现 |

顺序理由：S0先行（源或模型不通后面白写）；S1/S2纯本地可单测，S3才碰网络和钱，S4最后拼装。

### 7.2 验收标准（3天试运行后用户判）

机器项（出证据）：
- 3天×12轮采样，任务计划零中断（日志为证）
- 日报100%按时生成，降级发生时有标注（不许静默）
- 单测 + dry-run 全绿

质量项（用户读日报判）：
- 快讯档：抽5条A级，认为值得提前做者至少3条
- 趋势档：3天里至少抓到1个后来真起来的话题
- 误报：A级里明显不该报的（纯广告/纯明星八卦且不属目标赛道）每天不超过1条
- 达标转正式使用+写复盘调权重；不达标按误报类型调阈值/赛道词再试3天

### 7.2.1 明确的不做（防蔓延）

不做小红书/抖音源、不做代理池、不做Web服务器（看板保持静态文件）、不做账号体系、不做自动发文——这工具只回答该做什么选题，不替你做内容。

### 7.3 用户需提供的两样东西

1. 微博 Cookie（S0，可选，缺了降级跑）
2. Server酱 SendKey（S4，微信扫码1分钟）
